This branch is **separate from** `graft-fl-aiscalar-20261113`. The original frozen 100-bug selection, evidence, experiment configs, archives and aggregate are unchanged. The scripts below are **offline** and make no Ollama calls.

## Reproduce the forensic report on AIScalar

```bash
cd ~/RAVE_FL_Research/GRAFT_FL_New_Run
conda activate rave-fl
git fetch origin graft-fl-recovery-analysis-20261116
```

**Do not** rerun `launch-all` or delete existing caches. Run the offline tests and diagnostics first.

## Recovery policy

1. Confirm candidate uniqueness and parser defects on local buggy checkout, inspect exact code paths, and document a targeted fix.
2. Keep the original selection SHA `a27224d014f0fa8c4c9ca431e3cd9e264342be1c58e40ce0024392df33c486b6`.
3. Preserve the exact same model, gold-free evidence, BM25 candidate count (24), two graph-call cap, and 9,000-byte collection limit.
4. Record source-code changes as a new corrected implementation version. Existing scores remain the immutable original run.
5. Attempt only affected original batches after passing an independent preflight. Do not silently substitute bugs or fill missing pairs with zeros.
6. Report recovered sample size and missingness separately; do not use recovered results to retroactively tune the held-out evaluation protocol.

## Graph-effect diagnosis

The offline postmortem records exact graph candidate IDs, overlap between focused and test-aware, stop-gate candidates, counts and per-policy MRR. It **does not claim that identical file MRR means identical method-level rankings or outputs**. The next deeper step must inspect raw request ledgers and the per-bug result traces, preserving provider provenance. Compare model responses and candidate-level ranking changes before claiming the mechanism.

## Random Forest feasibility

Target: predict whether a new graph inspection will improve file MRR compared to L1. Features must be available **before** that graph inspection and before gold is revealed. Train/calibrate **only on development**; evaluation is held out.

The archived 14 completed development bugs have **zero observed positive file-MRR gains**, for either fusion. This creates a one-class target. Therefore, a supervised Random Forest cannot be meaningfully trained or evaluated on the available development examples. The feasibility script explicitly reports this and trains nothing. It does not make up labels, use evaluation outcomes for training, or claim accuracy improvement.

A future *newly registered condition* can collect useful candidate-specific and intermediate-ranking variation on development cases, with independently held-out tests. Compare RF gating to always-L1, always-graph, and a non-learned uncertainty threshold by file MRR, Top-1, graph calls, physical tokens and latency. No model inference or RF results have been generated by this branch.
